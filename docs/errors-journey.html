1) الصورة الكبيرة: 4 حاجات بنسميهم كلهم "error"

أغلب اللخبطة بتحصل إن فيه 4 كيانات مختلفة، وكل واحد له مكان ومسؤولية. الخطأ إن أي واحد يعدّي حدود مرحلته.

#الكيانالطبقةشكلهمين المسؤول عنهمثال في كودك
1ExceptionDataكلاس بيترمي بـ throwالـ datasource / SDKAuthException('invalid_credentials')
2FailureDomainكلاس بيرجع في Either.Leftالـ repositoryAuthFailure(code: 'invalid_credentials')
3StatePresentationكلاس sealed بيتبعت من البلوكالـ BlocSigninBlocError(failure: ...)
4Translation KeyPresentationString زي errors.auth.invalid_credentialsالـ Mapper + json"الايميل أو الباسورد غلط"
القاعدة الذهبية: Exception ميعبرش حدود الـ data. Failure ميعبرش حدود الـ presentation. الـ State مش شايل نص للمستخدم. النص بيتولد في آخر لحظة من ملف JSON.

كل واحدة من دول ليها سبب وجود:

  • Exception موجود لأن SDK بترمي، ومفيش طريقة تانية تتعامل بيها مع مكتبة مش بتاعتك.
  • Failure موجودة عشان الـ domain ميعرفش Supabase. لو بكرة استبدلنا Supabase بـ REST API، الـ Failures تفضل زي ما هي.
  • State موجود عشان الواجهة تتعامل مع حالات محدودة معروفة (closed set) بدل boolean متشعبة.
  • Key موجود عشان اللغة. لو كتبت النص العربي جوه الـ Bloc، مش هتقدر تعمل إنجليزي أبدًا.

5) الـ _guard — نقطة التحويل

Future<Either<Failure, T>> _guard<T>(Future<T> Function() call) async {
  try {
    return Right(await call());
  } catch (e) {
    return Left(FailureMapper.map(e));
  }
}

// كل دالة في الريبو سطر واحد:
@Override
Future<Either<Failure, UserEntity>> signInWithEmail(SigninParams params) =>
    _guard(() => authRemoteDataSource.signInWithEmail(params));

ليه generic <T>؟

عشان نفس الكود يخدم UserEntity وvoid وbool وAuthUserResult. من غير generic هتكتب 7 نسخ متطابقة.

ليه بنمسك Object مش Exception؟

لأن catch (e) بيمسك أي حاجة اترمت، حتى لو Error (زي TypeError). ولو كتبت on Exception catch (e) هتفلت الأخطاء اللي بتيجي من الـ casting — وهي بالظبط اللي محتاجين نمسكها.

ليه مفيش rethrow؟

لأن عقد الريبو بيقول: بيرجع Either، ومش بيرمي. لو رميت برّه، الـ Bloc هيقع والـ fold مش هيتنفذ أبدًا.

الحالة الوحيدة اللي مسموح فيها بـ throw

الـ datasource — لأنه بيتكلم مع مكتبة خارجية عقدها throw. ومفيش try/catch فاضي حواليه، لأن ده كود ميت (بيمسك ويرمي تاني نفس الحاجة).

6) الـ FailureMapper — جدول التحويل

abstract class FailureMapper {
  static Failure map(Object error) {
    return switch (error) {
      AuthException() => AuthFailure(
          message: error.toString(),
          code: error.code ?? 'unknown',
        ),
      PostgrestException() => ServerFailure(message: error.toString()),
      StorageException() => ServerFailure(message: error.toString()),
      SocketException() => NetworkFailure(message: error.toString()),
      _ => ServerFailure(message: error.toString()),
    };
  }
}

اللي شغال صح

  • switch على النوع بـ object pattern (AuthException()) — بيمسك الـ subclasses كمان، زي AuthApiException وAuthWeakPasswordException، لأنهم extends AuthException.
  • الترتيب: الحالات الأخص الأول. _ في الآخر كـ fallback مضمون.
  • مكان واحد بس — لو عايز تضيف نوع جديد تعدّل سطر واحد.

اللي ناقص (وهو اللي هنشتغل عليه)

#النقصالأثر العملي
1مفيش branch لـ FunctionExceptionأي خطأ من Edge Function (زي check-email-exists وهو واقع) بيروح _ → ServerFailure → "حدث خطأ". مش كارثة بس مش دقيق.
2مفيش branch لـ AuthRetryableFetchExceptionدي اللي بتترمي لما الشبكة تقع أثناء auth. هي subclass من AuthException → بتتحول AuthFailure مع code: null → 'unknown'، بدل ما تتحول NetworkFailure. يعني "الشبكة واقعة" بتظهر "حدث خطأ".
3مفيش branch لـ http.ClientExceptionعلى الموبايل أحيانًا الفشل بيطلع من طبقة http مش من Socket مباشرة. لو ممسكتهاش → ServerFailure.
4PostgrestException.code بيضيعالكود فيه معلومات ذهبية: 23505 = unique violation (إيميل متسجل)، 42501 = RLS رفض، PGRST116 = صف مش موجود. دلوقتي كلهم "حدث خطأ".
5بيبلع الـ exception الأصليمفيش debugPrint ولا log. لو المستخدم قال "بيظهرلي خطأ"، مفيش أي أثر تقدر تتتبعه.
6مفيش تمييز بين TypeError وبين فشل سيرفرغلطة في الـ schema بتظهر كأنها مشكلة شبكة. صعب جدًا تتشخص.

7) شجرة الـ Failures

Failure (abstract, Equatable)
├── ServerFailure       message            [مستخدم]
├── NetworkFailure      message            [مستخدم]
├── LocalFailure        message            [معرّف وغير مستخدم]
├── MatchMakingFailure  message            [معرّف وغير مستخدم]
├── BattleFailure       message            [معرّف وغير مستخدم]
├── AuthFailure         message + code     [مستخدم]
└── CacheFailure        message            [معرّف وغير مستخدم]
الكلاسمين بيرجّعه دلوقتيملاحظة
AuthFailureأي AuthExceptionالوحيد اللي شايل code — وده اللي بيخلي الترجمة ممكنة
ServerFailurePostgrest / Storage / أي حاجة متعرفشمفيش code → الترجمة بتقف عند "حدث خطأ"
NetworkFailureSocketException فقطنادرًا ما بيتفعّل (شوف §6 نقطة 3)
LocalFailure … CacheFailureولا حدمستقبلية — سيبهم
باج حقيقي في failures.dart: Failure.props => [message]، وAuthFailure مش بتعمل override. يعني: 
AuthFailure(message: 'x', code: 'user_not_found')
  == AuthFailure(message: 'x', code: 'email_not_confirmed')   // true ❗
السبب: الـ Equatable بتقارن props، والـ code مش موجود فيها. والنتيجة إن البلوك ممكن ميبعتش الحالة الجديدة، أو إن مقارنة حالتين مختلفتين تطلع متساوية. نفس الغلطة اللي كانت في SigninBlocError قبل ما تتصلح.

ليه AuthError مختلف؟

لأنه مش ناتج عن فورم معيّن، هو حالة عامة للتطبيق (sign out فشل مثلًا)، والـ router بيعتمد عليه: AuthError() => AppRoutes.signin. لكنه مش شايل Failure — يعني مستحيل تعرض رسالة دقيقة، ومستحيل تفرّق بين خطأ شبكة وخطأ صلاحيات.

9) من Code لنص عربي

class AppErrorTitleMapper {
  static String toKey(Failure failure) => switch (failure) {
    NetworkFailure() => 'errors.network',
    AuthFailure(:final code) => switch (code) {
      _ when code.contains('invalid_credentials') => 'errors.auth.invalid_credentials',
      _ when code.contains('email_not_confirmed') => 'errors.auth.email_not_confirmed',
      _ when code.contains('user_not_found') => 'errors.auth.user_not_found',
      _ => 'errors.unknown',
    },
    _ => 'errors.unknown',
  };
}

10) مسارات الواجهة الثلاثة

أ) SignInScreen — BlocConsumer

if (state is SigninBlocError) {

المسار ده سليم: failure → key → tr → toast. ملاحظة صغيرة: AppErrorDescMapper.toKey(...)?.tr() لو رجعت null الناتج null وAppToast بيتعامل معاه (description != null) — تمام.

ب) SignUpScreen — BlocListener

نفس الفكرة مع SignUpError. زائد حالة منفصلة (EmailIsExist) بتعرض رسالة الإيميل المتسجل من مفاتيح مباشرة مش من الـ mapper:

if (state is EmailIsExist && state.isExist) {
  AppToast.show(title: 'errors.auth.email_already_exists'.tr(), ...);
}

ده مقبول لأنه مش ناتج عن Failure أصلاً (الـ Edge Function بترجّع bool). بس يبقى في دماغك إن فيه مسارين مختلفين لإظهار رسالة إيميل متسجل: واحد من الـ mapper (لو Supabase رفضت) وواحد مباشر (لو الـ Edge Function قالت موجود).

ج) CharacterChoiceScreen — رسالة ثابتة

if (state is CharacterIError) {
  return _buildLoadFailure(context: context, message: "errors.unknown".tr());
}

المشكلة: الـ state شايل failure وmessage، والواجهة بتتجاهل الاتنين وتكتب نص ثابت. يعني أي خطأ في تحميل الشخصيات — حتى لو شبكة — بيطلع "حدث خطأ".

د) AuthError — خطأ صامت

الـ router بيعمل redirect لـ /signin لما الحالة AuthError — ومفيش أي toast. حاليًا AuthError بيتولد في حالتين: فشل sign out، وفشل فتح Google OAuth. يعني لو Google فشل، المستخدم بيرجع لشاشة الدخول من غير أي تفسير. ده أخطر مسار UX في القائمة.

AuthException('email_not_confirmed')EmailConfirmationRequiredExceptionالحالة دي مش خطأ من السيرفر، دي نتيجة (result) محتاجة تصرف مختلف
نقطة تصميم مهمة: email_not_confirmed أصلاً مش "خطأ" — هي نتيجة متوقعة. بدل ما ترميها كخطأ وترجع لشاشة الدخول، الأفضل (مستقبلًا) إن الريبو يرجّع Result منفصل ويودّيه على شاشة "فعّل إيميلك". حاليًا أسيبها كـ Failure لحد ما نبني الشاشة.

12.2 الـ mapper بعد التعديل — الشكل المستهدف

static Failure map(Object error) => switch (error) {
  NetworkException()      => NetworkFailure(...),
  SocketException()       => NetworkFailure(...),
  ClientException()       => NetworkFailure(...),          // http
  AuthRetryableFetchException() => NetworkFailure(...),    // قبل AuthException

  ProfileMissingException()            => AuthFailure(code:'user_not_found'),
  EmailConfirmationRequiredException() => AuthFailure(code:'email_not_confirmed'),
  InvalidCredentialsException()        => AuthFailure(code:'invalid_credentials'),
  AuthSignUpFailedException()          => AuthFailure(code:'signup_failed'),

  FunctionException()     => ServerFailure(...),
  PostgrestException()    => ServerFailure(code: error.code, ...),
  StorageException()      => ServerFailure(...),
  TypeError()             => DataFailure(...),   // اختياري
  _                       => ServerFailure(...),
};
ترتيب الحالات مش رفاهية: AuthRetryableFetchException لازم تيجي قبل AuthException، لأنها extends AuthException — نفس الكلام على FunctionsFetchException قبل FunctionException. لو عكست الترتيب، الحالة الأخص مش هتتنفذ أبدًا.

12.3 الـ Failure بعد التعديل

class AuthFailure extends Failure {
  final String code;
  const AuthFailure({required super.message, required this.code});
  @override
  List<Object?> get props => [message, code];   // ← السطر الناقص
}

class ServerFailure extends Failure {
  final String? code;        // ← جديد: كود Postgres (23505 / 42501 / PGRST116)
  const ServerFailure({required super.message, this.code});
  @override
  List<Object?> get props => [message, code];
}

14) قرارات وقواعد تاخدها معاك

السؤالالقرارالسبب
ليه مش rethrow وخلاص؟مفيش rethrow في catch فاضيكود ميت: بيمسك ويرمي نفس الحاجة. لو مش هتعمل حاجة، شيل الـ try/catch
هل أكتب نص للمستخدم في الـ data layer؟لأالـ data ميعرفش لغة ولا شاشة. تكتب code، والـ presentation تترجم
code String ولا enum؟String حاليًا، enum لاحقًاenum بيمنع الأكواد الغلط وقت الـ compile. بس محتاج طبقة تحويل من كود Supabase لـ enum بتاعك
هل الـ Bloc يستخدم failure.message في الواجهة؟لأ، ولا مرةالـ message نص تقني (أحيانًا إنجليزي من السيرفر). الواجهة تستخدم الـ key
هل نحتفظ بـ message في الـ Failure أصلًا؟آه، للتشخيص والـ logsمش للعرض. وهي كمان بتدخل في props فبتفرّق الحالات
هل كل failure لازم يبقى لها state؟لأالـ state بيمثل حالات الواجهة الممكنة. مثلاً AuthFailure(code:'weak_password') وinvalid_credentials نفس الـ state، الرسالة بس مختلفة
إزاي أعرف إن الشبكة واقعة قبل ما أجرب؟متختبرهاش بالتخمينافصل الـ wifi واعمل sign in. لو ظهر "حدث خطأ" يبقى الـ AuthRetryableFetchException مش متغطي

أسئلة تشخيص سريعة (تستخدمها وقت أي خطأ)

  1. الشاشة عرضت إيه؟ لو "حدث خطأ، حاول مرة أخرى" → يبقى الـ errors.unknown، يعني الـ code مش متغطي في AppErrorTitleMapper.
  2. الـ state وصل ولا لأ؟ لو مفيش أي toast، يبقى إما البلوك مبعتهاش (props متساوية) أو الـ listener مش موجود.
  3. الـ Failure نوعه إيه؟ ضيف debugPrint('${failure.runtimeType}') مؤقتًا.
  4. لو ServerFailure → شوف الـ log: PostgrestException ولا TypeError؟
  5. لو AuthFailure(code: 'unknown') → الـ SDK رمى AuthException من غير code (غالبًا شبكة أو session).

15) ملخص في 6 سطور

  1. الخطأ بيتولد Exception في الـ data، ويتحول Failure في الـ repository عبر _guard + FailureMapper.
  2. الـ Bloc بيحوّل الـ Failure لـ State بـ fold، والواجهة بتحوّل الـ State لـ key عبر AppErrorTitleMapper ثم نص من الـ json.
  3. الكود الحالي سليم في العمود الفقري، وناقص في: AuthFailure.props، واستعارة AuthException، وتغطية أكواد Supabase، وتفصيل PostgrestException.
  4. أخطر ثقب UX: AuthError صامت — فشل Google بيرجّع المستخدم لشاشة الدخول من غير رسالة.
  5. أخطر ثقب تطويري: مفيش logging للـ exception الأصلي، فكل خطأ بيبان "حدث خطأ" ومفيش أثر تتتبعه.
  6. الخطة: failures → exceptions → mapper → datasource → error_mapper → json → character repo → character UI → AuthError → logging.
